# ADR-0005: 서버 → 로컬 상태 역동기화(pull) + 주문 그룹 hard delete

- **Date**: 2026-07-30
- **Status**: Accepted
- **이슈**: #70

## Context

로컬·서버는 역할이 분리돼 있다. 예약은 로컬(Playwright), **운송장 스크래핑과 네이버
발송처리는 서버 단독**이다. 동기화는 로컬 → 서버 **단방향**(`/api/internal/*`)이고,
서버는 로컬을 호출할 수 없다(로컬 Mac은 공개 주소가 없다).

그래서 발송 결과가 로컬로 돌아오는 경로가 사실상 없었다.

1. **유일한 역동기화 트리거가 잘못된 시점에 있었다.** `resyncBookedOrders()`는 예약 큐가
   비는 순간(`gs-delivery/worker.ts`) 호출되고, 서버가 응답에 담아주는 `allDispatched`
   플래그로만 로컬을 정리했다. 그런데 그 시점은 **예약 직후 = 서버가 운송장을 잡기 몇 분 전**
   이라 방금 예약한 배치는 항상 "아직 발송 안 됨"으로 나온다. 그리고 다시는 호출되지 않는다.
2. **동기화 버튼은 도움이 안 된다.** `POST /api/orders/sync`는 네이버 *발송대기* 주문만
   가져온다. 이미 발송처리된 주문은 네이버 응답에서 빠지므로 로컬 row는 영원히
   `booked` + 운송장 NULL로 남는다 → 화면에는 "운송장 대기 중..."이 계속 표시된다.
3. **로컬에서 손댄 건은 아예 대상 밖이었다.** `getLocalBookedOrders()`는 `status='booked'`만
   조회한다. 사용자가 "왜 안 없어지지" 하고 수동으로 실패로 옮긴 그룹은 역동기화 후보에서
   빠져 영구 고착된다. 예약번호가 없는 그룹도 `continue`로 건너뛴다.
4. **운송장이 로컬로 회수되지 않는다.** `markOrderGroupAsDispatched()`는 상태·발송시각만
   쓰고 `trackingNumber`는 채우지 않아, 로컬 dispatched row에 운송장이 비어 있다.

실측(로컬/서버 DB 대조, 2026-07-30):

| 그룹 | 로컬 | 서버 |
|------|------|------|
| A (5건) | booked, 운송장 NULL | dispatched 07-30 03:44Z |
| B (2건) | booked, 운송장 NULL | dispatched 07-30 03:44Z |
| C (2건) | failed (사용자 수동 이동) | dispatched 07-28 04:00Z |
| D (1건) | failed (사용자 수동 이동) | dispatched 07-28 04:00Z |

A·B는 로컬 예약 03:37~03:38Z → 큐 드레인 시 역동기화 → 서버 발송 03:44Z. **6분 차이로
어긋난** 전형적인 사례다.

또한 운영상 요구가 하나 더 있었다: 동기화로 목록에 올라온 주문을 **취소하고 싶을 때
지울 방법이 없다**. 상태 변경(대기/완료/실패)만 가능해 목록에 계속 남는다.

## Decision

### 1. 역동기화는 로컬이 서버에 묻는 pull 방식으로 한다

- 서버에 **읽기 전용** 조회 엔드포인트를 신설한다: `POST /api/internal/order-state`
  (`{orderIds}` → 그룹별 `status`/`dispatchStatus`/`trackingNumber`/`dispatchedAt`).
- 로컬은 `reconcileFromServer(orderIds?)`로 미완결 그룹(`booked`/`booking`/`failed`,
  최근 2주)을 서버에 물어 로컬 DB를 정정한다. 발송 관련 필드는 **항상 서버가 진실**이다.
- 상태 전이 판정은 DB에 의존하지 않는 순수 모듈 `lib/order-lifecycle.ts`로 분리한다
  (`aggregateGroupState`, `resolveServerStateSync`). `lib/orders.ts`는 import 시점에 실제
  SQLite 파일을 열기 때문에, 정책 로직을 분리하지 않으면 테스트가 사용자 DB를 건드린다.
- 호출 지점을 **3곳**으로 늘린다:
  - `POST /api/orders/sync` (동기화 버튼) — 네이버 조회 **전에** 실행. 사용자가 "안 없어지네"
    라고 느낄 때 가장 먼저 누르는 버튼이 곧 복구 경로가 된다.
  - `POST /api/dispatch/manual-now` step 0 — 이미 발송된 건을 먼저 걷어내 불필요한 GS
    스크래핑·세션 프로브를 줄인다(봇 감지 리스크 감소).
  - 예약 큐 드레인 직후(`resyncBookedOrders()` 다음) — 지난 배치 회수용. 방금 예약한 건은
    여기서 안 잡히는 것이 정상이며, 위 두 경로가 담당한다.
- 그룹 단위 판정에서 `dispatched`는 **모든 row가 dispatched일 때만** 인정한다(부분 발송을
  완료로 오인 방지). 서버가 운송장만 잡은 단계면 `booked` + 운송장·발송상태만 반영한다.
- 로컬에도 `dispatched`가 생기므로 **로컬 대시보드에 발송완료 탭을 추가**한다. 없으면
  예약완료 탭에서 조용히 사라져 "발송된 건지 유실된 건지" 구분할 수 없다.

### 2. 주문 그룹 삭제는 tombstone 없는 hard delete로 한다

- `DELETE /api/orders/group?orderId=...` — `orders` + 연결된 `bookingLogs`를 함께 지운다.
- **대기·예약완료·실패·건너뜀** 상태를 모두 삭제할 수 있다.
- 삭제 흔적(tombstone)을 남기지 않는다. 네이버 동기화는 `productOrderId` upsert이므로,
  네이버에 아직 발송대기로 남아 있는 주문은 **다음 동기화에서 자연히 다시 수집된다**.
  이는 요구사항("대기 상태에서 삭제한 건도 네이버에 남아있으면 다시 수집")을 정확히 만족한다.
- **삭제는 서버에도 전파한다**(`DELETE /api/internal/orders`). 로컬에서만 지우면 서버 폴링이
  그 주문을 계속 추적해 네이버로 발송처리한다 → "취소하려고 지웠는데 발송됨"이 된다.
- **예약완료·실패 그룹은 삭제 직전에 그 그룹만 역동기화**한다. 서버가 이미 발송했으면
  삭제를 거부(409)하고 로컬을 발송완료로 정정한다.
- 삭제 불가 상태는 둘이다:
  - `booking` — 로컬 Playwright 워커가 해당 row를 잡고 있다(예약 취소 후 삭제).
  - `dispatched` — 이미 출고돼 되돌릴 수 없고, 네이버에서 재수집도 안 되므로 기록만 사라진다.
- 삭제는 **이 앱의 목록에서만 제거**한다. GS택배 예약·네이버 주문은 취소되지 않는다.
  오해하면 실제로 물건이 배송되므로 확인 다이얼로그에 이 사실을 명시한다.

## Alternatives

- **(A) 서버 → 로컬 push (웹훅/역방향 동기화)**: 발송 즉시 반영돼 가장 실시간이지만, 로컬
  Mac은 공개 주소가 없고 켜져 있지도 않다. 터널링(ngrok 등)은 상시 인프라와 인증 표면을
  새로 만든다. 기각.
- **(B) 예약 후 N분 뒤 재동기화 예약(setTimeout)**: 큐 드레인 시점 문제만 미룬다. N을 짧게
  잡으면 여전히 어긋나고, 길게 잡으면 그 사이 로컬이 꺼진다(로컬은 상시 구동이 아니다).
  기각.
- **(C) 로컬 폴링(로컬이 주기적으로 서버 조회)**: 사람이 앱을 열지 않는 시간에도 돌아
  전기·요청만 쓰고, 정작 화면을 볼 때 최신인지는 보장하지 않는다. "사용자 행동(동기화/발송
  버튼)에 얹는" 방식이 같은 효과를 더 싸게 낸다. 기각.
- **(D) 로컬 DB를 서버 DB로 통합(단일 DB)**: 근본 해결이지만 로컬 Playwright가 원격 DB에
  의존하게 되고(오프라인 예약 불가), 마이그레이션·백업 전략을 새로 짜야 한다. 현 아키텍처
  전제를 뒤집는 규모. 기각.
- **(E) 삭제를 soft delete(tombstone)로**: 삭제 이력이 남아 감사에 유리하지만, 네이버
  재수집이 tombstone에 막힌다. 예외 규칙(대기 상태만 재수집 허용 등)을 넣으면 upsert 경로가
  복잡해진다. 요구사항이 "다시 수집되게"이므로 hard delete 채택.
- **(F) 발송완료도 삭제 허용**: 요구는 "대기·예약완료·실패 상관없이"였고 발송완료는 목록에
  없었다. 발송완료를 지우면 네이버 재수집도 안 되고 배송 추적 기록만 잃는다. 제외.

## Consequences

### 긍정
- "서버는 발송했는데 로컬은 운송장 대기중" 상태가 **동기화 버튼 한 번으로 정리**된다.
  사용자가 수동으로 실패 처리해둔 과거 잔재(C·D)도 같은 경로로 회수된다.
- 운송장번호가 로컬로 회수돼, 로컬 dispatched row의 운송장 공백(`markOrderGroupAsDispatched`
  갭)도 함께 메워진다.
- 발송 판정 로직이 순수 함수로 분리돼 실제 DB 없이 테스트된다.
- `manual-now`가 이미 발송된 건을 스크래핑하지 않아 GS 봇 감지 노출이 줄어든다.
- 취소한 주문을 목록에서 치울 수 있고, 서버까지 전파되므로 "지웠는데 발송됨"이 막힌다.

### 부정 / 모니터링 포인트
- **서버 연결 실패 시 역동기화는 조용히 건너뛴다**(`ok:false`, 로컬 DB 무변경). 네이버
  동기화는 계속 진행되므로 사용자는 실패를 즉시 알 수 없다. 반복되면 로그(`[sync]`) 확인 필요.
- **로컬이 진실인 필드와의 경계**: 서버가 진실인 것은 발송 관련 필드뿐이다. 예약 진행/취소
  같은 로컬 전용 상태는 건드리지 않는다. 이 경계를 넘는 필드를 추가할 때 재검토가 필요하다.
- **삭제 후 재수집 타이밍**: 대기 주문을 지운 직후 동기화하면 바로 다시 올라온다(의도된
  동작). "안 지워졌다"로 오해할 수 있어 다이얼로그에 재수집 안내를 넣었다.
- **서버 삭제 전파는 best-effort**: 서버가 응답하지 않으면 서버 row가 남는다. 이때 서버
  폴링이 발송할 수 있으므로, 삭제 실패 로그(`[sync]`)가 반복되면 서버 상태를 직접 확인해야 한다.
- **조회 범위 2주 / 최대 300건**: 그보다 오래된 고착 건은 자동 회수되지 않는다. 현 운영
  물량에선 충분하나, 물량이 늘면 페이지네이션이 필요하다.

### ADR-0003·0004와의 관계
Supersede 아님(**보완**). 0003(수동 즉시 발송)·0004(예약 후 1시간 스크래핑)는 "운송장을
언제 잡을까"를 다룬다. 0005는 그 결과가 **로컬 화면까지 돌아오는 경로**를 만든다.
