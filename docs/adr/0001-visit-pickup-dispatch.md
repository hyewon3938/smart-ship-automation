# ADR-0001: 방문택배 자동 발송처리 — 폴링 트리거 + 마스킹 매칭

- **Date**: 2026-05-28
- **Status**: Accepted
- **이슈**: #59

## Context

방문택배는 일반 GS편의점 택배와 흐름이 다르다:

1. **결제 책임 분리**: Playwright가 폼 자동 입력은 하지만 "예약하기" 버튼은 누르지 않는다.
   사용자가 브라우저에서 직접 결제하고 예약을 확정한다. 시스템은 결제 완료 시점이나
   생성된 예약번호를 자동으로 인지하지 못한다.

2. **1:N 운송장 구조**: 1 방문택배 예약 안에 N명 수령인 + N개 운송장이 함께 들어있다
   (일반택배는 1:1). GS 예약list 페이지에는 운송장이 한 셀에 줄줄이 나열되어 있고,
   상세 페이지의 "수신정보" 섹션에서 수령인별로 운송장이 분리된다.

3. **수신정보 마스킹**: 상세 페이지의 수신정보는 기본 마스킹 상태로 표시된다.
   - 이름: `문*진` (첫 글자 + 끝 글자만)
   - 주소: `[47180] 부산광역시 부산진구 당감로25번길 19 ******` (우편번호 + 도로명까지만)
   - 전화: `010-****-5655` (앞 3자리 + 끝 4자리)
   - **운송장번호는 unmasked** (배송 추적용으로 항상 노출)

4. **마스킹 해제 비용**: "숨김 해제" 버튼은 Cloudflare Turnstile 캡챠를 요구한다.
   자동화 시 봇 감지 위험.

5. **사용 빈도**: 사용자 진술에 따르면 방문택배는 자주 발생하지 않음. 단순성을 우선해도 됨.

## Decision

두 가지를 함께 결정.

### D1. 결제 완료 트리거 = 폴링만

- 기존 `dispatch-worker`가 11\~18시 KST에 2분 간격 폴링 중. 이 폴링 사이클에 방문택배 처리도 합류.
- GS 예약list 페이지를 HTTP fetch로 가져와서 "구분 = 방문" 행을 발견하면 해당 예약을 처리 대상으로 본다.
- 로컬 DB에서 `status="booking" AND selectedDeliveryType="visit"` 인 그룹들 중 매칭되는 그룹을 찾아 처리.
- 사용자는 결제 후 따로 트리거할 필요 없음.

### D2. 수령인 → 운송장 매칭 = 마스킹 그대로

- 매칭 키: **(우편번호, 전화번호 끝 4자리)** 튜플
- 한 방문택배 안 N명(5\~9) 수준에서 이 튜플의 충돌 확률은 사실상 0
- 매칭 알고리즘:
  1. 상세 페이지에서 수신정보 블록들을 파싱 — 각 블록에서 `[XXXXX]` 우편번호 +
     `010-****-NNNN` 끝 4자리 + `<a class="num">XXXXXXXXXXXX</a>` 운송장번호 추출
  2. 로컬 DB의 booking 방문 주문에서 `(recipientZipCode, recipientPhone.slice(-4))` 키 생성
  3. 매칭 → 해당 그룹에 `bookingReservationNo` + `trackingNumber` 저장 → status=`booked`
  4. 이후는 기존 일반택배 발송처리 흐름 합류 (네이버 dispatch API 호출)

## Alternatives

### 트리거 대안

- **자동 감지 (Playwright가 결제 완료 페이지 도달까지 대기)**
  - 정확하지만 사용자가 페이지를 닫거나 다른 탭에서 결제하면 영영 놓침
  - 메모리 상의 Playwright context를 결제 끝날 때까지 붙들고 있는 것도 부담

- **수동 트리거 (대시보드 "결제 완료" 버튼)**
  - 명시적 확인 가능하지만 사용자 액션 추가 → 깜빡할 가능성
  - 방문택배 처리 흐름에 사용자 책임 두 번 (결제 + 트리거)

→ 단순성 우선. 폴링은 일반택배에서 이미 검증된 패턴이므로 합류시키는 게 안전.

### 매칭 대안

- **입력 순서 매칭** (Playwright가 입력한 수령인 순서 = 상세 페이지 표시 순서)
  - 단순하지만 GS가 입력 순서를 영구 보장한다는 확신 어려움 (정렬 변경 등 1회 발생 시 전 건 오매칭)
  - 검증 비용이 마스킹 매칭 도입 비용보다 크다고 판단

- **마스킹 해제 후 정확히 매칭** (Cloudflare Turnstile 우회)
  - 100% 정확하지만 자동화 비싸고 봇 감지 위험
  - 마스킹 그대로 매칭이 충분히 unique 한 상황에서 ROI 낮음

## Consequences

### 긍정

- Cloudflare Turnstile 우회 안 함 → 봇 감지 위험 회피, 자동화 단순
- 사용자 추가 액션 0 → 일반택배와 같은 UX
- 매칭 키 단순 (zip + 끝4) → 로그/디버깅 직관적
- 일반택배 폴링 사이클에 합류 → 추가 인프라 0

### 부정 / 모니터링 포인트

- **2분 폴링 지연**: 결제 후 \~2분 안에 발송처리 시작. 허용 범위.
- **11\~18시만 처리**: 기존 일반택배와 동일 제약. 합리적.
- **GS 마스킹 정책 변경 위험**: GS가 우편번호 또는 전화 끝4자리까지 마스킹하면 매칭 불가.
  → 매칭 실패율을 로그로 추적. 매칭 실패 시 booking 상태 유지하고 경고 로그.
- **`selectedDeliveryType` enum 확장**: 기존 `"domestic" | "nextDay"` 에 `"visit"` 추가.
  의미적으로 "delivery type"이 약간 확장되지만 사용자 관점에서 같은 카테고리(택배 종류).
  새 필드 추가보다 단순.
